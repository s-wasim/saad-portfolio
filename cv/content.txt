HOW TO EDIT THIS FILE
=====================
Every piece of text on the site lives here. Each entry is a header line, then
its text on the lines below it. A header looks like this one, for the WORK tab:
<!-- WORK | document_pipeline card / title -->  (on a line of its own)

  * Change the text under a header. Leave the header line exactly as it is:
    it is how the site finds where that text goes.
  * An entry runs until the next header. Blank lines around it are ignored.
    Page text wraps by itself, so a line break inside a paragraph shows as
    a space.
  * Entries marked "(one per line)" are lists: one item per line. Add or
    delete lines freely.
  * Words in braces, like {name}, are filled in by the site. Keep each one,
    spelled exactly the same (you can move it within the sentence).
  * Never type two opening braces in a row.

Run these from the fe_design_complete folder (the one that holds this file):
Preview on your computer:   python3 tools/preview.py
Check for mistakes:         python3 tools/check_text.py
GitHub runs the same check on every push and marks the commit with a red X if
a header doesn't match. Lines above the first header (like these) are notes;
the site ignores them.

ch 02 · method

<!-- METHOD | Header / title -->
METHOD

<!-- METHOD | Header / intro -->
How a document becomes a row in a database. Five steps, the same five every time. Scroll: the diagram holds still and lights the part being described.

<!-- METHOD | Step 1 / label -->
STEP 01 · SHAPE

<!-- METHOD | Step 1 / heading -->
Draw the state machine first

<!-- METHOD | Step 1 / text -->
Before any prompt gets written, the whole job is a graph on paper: nodes, edges, what state each node reads and writes. If it can't be drawn, it isn't understood yet. LangGraph because the graph is the artifact — not a crew of agents improvising a plan at runtime.

<!-- METHOD | Step 2 / label -->
STEP 02 · BUDGET

<!-- METHOD | Step 2 / heading -->
Count the model calls

<!-- METHOD | Step 2 / text -->
Three LLM calls per document, capped, and the cap is a test. Vision for classification, structured output for extraction, one repair if validation fails, and that's the budget. Every call that isn't in the budget is a cost you'll discover in production instead of in review.

<!-- METHOD | Step 3 / label -->
STEP 03 · SCHEMA

<!-- METHOD | Step 3 / heading -->
Make the model return a shape

<!-- METHOD | Step 3 / text -->
Structured output, schema-enforced, validated by code that has never heard of a language model. Cross-field logic is cheap and deterministic; use it. When validation fails, repair gets exactly one attempt — then it becomes a human's problem, on purpose.

<!-- METHOD | Step 4 / label -->
STEP 04 · GATE

<!-- METHOD | Step 4 / heading -->
Put the human where it matters

<!-- METHOD | Step 4 / text -->
Autonomy is not the goal — a correct write is. One approval gate, at the irreversible step, and the machine genuinely stops there. The amber indicator on this console is the same signal: hardware waits with the pipeline.

<!-- METHOD | Step 5 / label -->
STEP 05 · SHIP

<!-- METHOD | Step 5 / heading -->
Hand over something that runs

<!-- METHOD | Step 5 / text -->
Dockerfile, pytest suite, README that assumes nothing. 69 tests green on document_pipeline. The deliverable is a service your team can deploy and modify without me — not a notebook I have to be present to explain.
